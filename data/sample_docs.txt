RAG, or Retrieval-Augmented Generation, is a technique that combines a retrieval system with a language model. Instead of relying only on what a language model learned during training, RAG first retrieves relevant pieces of text from an external knowledge source, then feeds those pieces to the language model as context before it generates an answer. This has two major benefits: the model can answer questions about information it was never trained on, such as private company documents, and the answer can be grounded in a real source, which reduces hallucination and allows citations.

A typical RAG pipeline has two phases. The ingestion phase happens once, or whenever documents change. It involves loading raw documents, splitting them into smaller chunks, converting each chunk into a vector embedding using an embedding model, and storing those embeddings in a vector database. The query phase happens every time a user asks a question. It involves converting the user's question into an embedding using the same embedding model, searching the vector database for the chunks whose embeddings are closest to the question's embedding, and passing those chunks along with the original question to a language model, which generates a final answer.

Vector similarity search is usually done using cosine similarity or Euclidean distance between embedding vectors. Cosine similarity measures the angle between two vectors rather than their magnitude, which makes it well suited for comparing text embeddings where the direction of the vector captures meaning. A smaller angle, meaning a cosine similarity closer to one, indicates the two pieces of text are more semantically similar.

Chunk size is an important design decision in a RAG system. If chunks are too large, the embedding becomes a blurry average of multiple ideas and retrieval precision drops. If chunks are too small, individual chunks may lack enough context to be useful on their own, and the system may need to retrieve many chunks to reconstruct a full idea. A common starting point is a few hundred words per chunk with a small overlap between consecutive chunks so that ideas spanning a chunk boundary are not lost.

Common failure modes in RAG systems include retrieving irrelevant chunks because the embedding model does not capture domain-specific terminology well, generating answers that are not actually supported by the retrieved chunks because the language model relies on its own prior knowledge instead, and returning stale answers because the vector database was not updated after the source documents changed. Evaluating a RAG system typically involves checking both retrieval quality, such as whether the correct chunk was retrieved for a given question, and generation quality, such as whether the final answer is accurate and properly grounded in the retrieved chunks.
